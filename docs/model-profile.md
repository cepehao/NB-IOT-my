# Базовый профиль модели NB-IoT

## Проверенная реализация кандидата —2026-10-06

Реализация выполнена и проверялась реальным MATLAB R2025b/LTE Toolbox. Нормативные конфигурационные значения static-v1 ниже сохранены. Историческая дата и описание этапа проектирования не являются текущим статусом; актуальные измерения и границы приёмки находятся в performance-report.md и acceptance-coverage.md.

NPRACH presence:12публичных стартовых тонов, четыре symbol groups, joint quadratic partial regression; threshold0.005 с независимой noise/interference-калибровкой. Параметры принятых индексов: public-template SIC с оценёнными timing/CFO и коэффициентами из RX. Истинные UE/taps/число передатчиков не используются. Два UE одного NInit не разделяются presence-детектором; capture определяется последующим физическим Msg3/Msg4.

DL: CP/NRS coarse FFT-window search−16..24samples, CFO clamp±200Hz, selective1×1frequency/time averaging и received-pilot noise estimate. Ошибка задержки в отчётах означает выбранное FFT окно относительно первого пути. UCI остаётся безCRC и с документированным точным waveform alias; состояние BS защищено проверкой актуального контекста/назначения.

Системные результаты новой радио-версии не обязаны совпадать со старым ошибочным детектором. Чистые CPU-патчи проверяются на точное совпадение, radio-патчи — на сохранённые регрессии и независимые физические данные. Последовательный расчёт не требует Parallel Computing Toolbox; GPU-прототип остался отдельно, поскольку полный1UE расчёт оказался медленнее.

## Исторический профиль проектирования —2026-10-01

Дата: 2026-10-01. Версия профиля: `static-v1`. Параметры выбраны для детального планирования по поручению пользователя. Реализация не начата.

Профиль закрывает недостающие решения для ядра, Static и сбора данных. Пометка «ТЗ» означает прямое требование исходного документа; «решение» означает выбранный вариант исследовательской модели. Значения решений являются конфигурацией и не выдаются за обязательные параметры стандарта. Проверка установки MATLAB и корректности PHY относится к будущей реализации.

## Размещение и распространение

| Параметр | Принято | Основание |
|---|---|---|
| Геометрия | Кольцо с горизонтальными радиусами 10–1000 m | ТЗ §10 |
| Высоты | BS 30 m, UE 1.5 m | ТЗ §10 |
| Размещение | Равномерное по площади | Решение |
| Indoor | Ровно `round(0.30*N)` случайно выбранных UE | Доля из ТЗ, правило — решение |
| Расстояние для потерь | Трёхмерное: `sqrt(r2d^2 + (30-1.5)^2)` | Решение |
| Path loss | Log-distance; опорное расстояние 10 m, показатель 3.5 | Решение |
| Shadowing | Нормальная добавка в dB, среднее 0, sigma 8 outdoor / 10 indoor | Значения из ТЗ, трактовка — решение |
| Penetration | 0 dB outdoor / 20 dB indoor | ТЗ §13 |
| Усиления антенн | 0 dBi, дополнительные кабельные потери 0 dB | Решение |
| Fading | Три независимых комплексных Rayleigh-отвода; задержки 0, 0.3, 0.9 µs; средние мощности 0, −3, −6 dB | Решение |
| Динамика fading | Отводы постоянны в течение реализации 5 s, новая выборка в следующей реализации | Решение для неподвижных UE |
| UL/DL fading | Независимые отводы; общие геометрия, shadowing и penetration | Решение для FDD |
| Coverage class | Все UE используют одну сконфигурированную группу CE0 | Решение; автоматического перехода CE нет |

Формула модели:

```text
d3d = sqrt(x^2 + y^2 + (hBS-hUE)^2)
PLref = 20*log10(4*pi*fc*dRef/c)
PL = PLref + 10*n*log10(max(d3d,dRef)/dRef)
L = max(0, PL + shadowingDb + penetrationDb)
```

При 900 MHz `PLref` приблизительно 51.53 dB. Для `d3d = 1000 m` медианные потери около 121.53 dB до shadowing и penetration. Это выбранная параметрическая модель, пригодная для заданного диапазона расстояний; она не объявляется стандартной моделью городской макросоты. Высоты входят в трёхмерную дистанцию. Сохранённый сценарий содержит и компоненты потерь, и итоговый `L`.

Средние мощности отводов нормируются так, чтобы их сумма была 1. Реальные комплексные коэффициенты не нормируются отдельно для каждого UE: случайные провалы мощности являются частью fading. Реализуется обычный FIR-канал на отсчётах; дополнительный Communications Toolbox не нужен.

| Power control | Фиксированный насыщенный режим; power ramping 0 dB | Решение для исследования near-far |
| BS DL power | 23 dBm на активной полосе 180 kHz | Решение для малой соты исследовательского сценария |
| NF BS / UE | 5 dB / 7 dB | BS из ТЗ; UE — решение |
| Температура | 290 K | ТЗ §13 |

| CFO по времени | Постоянен для UE в одной реализации; при RX знак противоположен TX | Решение |
| Остаточная синхронизация | Один offset UE, равномерно от −2 до +2 µs | Решение |
| DL задержка | `d3d/c`, с исходной синхронизацией относительно принятого DL | Решение |
| Начальная UL задержка | `2*d3d/c + syncOffset`, включая привязку часов UE к принятому DL | Решение |
| Timing advance | По оценке NPRACH из RAR, округление к шагу `16/(15000*2048)` s, ограничение допустимым диапазоном команды | Решение на основе структуры TA |
| После RAR | Реальная задержка минус переданный TA; оставшаяся ошибка оценивается по пилотам | Решение |

Выбрана единая частота дискретизации 1.92 MHz для UL и DL. Совместимость с настройками `lteNPRACH`, SC-FDMA и OFDM проверяется в первом PHY-этапе; несоответствие исправляется в адаптере частоты дискретизации, сохраняя физические параметры профиля. Фазовые множители CFO вычисляются по абсолютному времени, включая интервал между передачами.

Комплексные отсчёты имеют нормировку мощности `mean(abs(x)^2)` в W. Передающий waveform нормируется по активным интервалам один раз; канал не нормирует суммарный сигнал по числу UE. Для белого комплексного шума `N0 = k*T*10^(NF/10)` W/Hz и `E|w|² = N0*Fs`. В генераторе каждая квадратура имеет дисперсию `N0*Fs/2`. После фильтрации в полосе B получается шум `N0*B`; для BS и 180 kHz он приблизительно −116.42 dBm.

Дробные задержки реализуются 65-коэффициентным оконным sinc-фильтром с косинусным окном, без дополнительного Toolbox. Групповая задержка реализации компенсируется временной меткой; хвосты и память FIR сохраняются. Шум BS генерируется один раз на общий UL; шум DL — отдельно для каждого UE.

## NPRACH

| Настройка | Принято |
|---|---|
| Format | 0 |
| Periodicity | 80 ms |
| StartTime | 8 ms внутри периода |
| SubcarrierOffset | 0 |
| NumSubcarriers | 12 |
| NRep | 1 |
| Выбор UE | Равномерный `NInit` 0–11 на допустимой возможности |
| Допуск Static | `accessProbability = 1` |
| Резервирование | Первые 45 kHz на 6 ms начиная с возможности; генератор сохраняет фактическую длительность |
| Передающие шаблоны | Все 12 вариантов из LTE Toolbox, кэшируемые по конфигурации |

Это проектные значения, отсутствующие в ТЗ. Реальная преамбула format 0 с одним повторением занимает около 5.6 ms; резервирование округлено вверх до шести системных тиков. Базовые значения генератора и семантика периодического буфера описаны в [lteNPRACH](https://www.mathworks.com/help/lte/ref/ltenprach.html). Нули вокруг сигнала не увеличивают занятую площадь и не входят в расчёт передаваемой мощности.

Для нескольких пользователей реализуется банк приёмных шаблонов. Для каждого из 12 `NInit` вычисляется максимум нормированной корреляции по известному окну и сетке CFO −200:25:200 Hz. Timing search — от −8 до +20 µs с шагом отсчёта и параболическим уточнением; затем CFO уточняется по повторяющимся символам. Шаблоны формируются Toolbox, поиск выполняется FFT-корреляцией с кэшированием, оконные/групповые энергии сохраняются для диагностики. По одному `NInit` возвращается один лучший кандидат; число передатчиков с одинаковым индексом не оценивается.

Граница поиска расширяется на задержку FIR после компенсации. Запись кандидата содержит `nInit`, `metric`, `threshold`, оценку delay/CFO и статус оценки. Приёмник перебирает все разрешённые индексы без списка реально передающих UE. Несколько разных кандидатов допустимы; SIC в первую версию не включается.

Штатный `lteNPRACHDetect` используется как эталон одиночного обнаружения и источник дополнительных метрик, но его один возвращённый максимум не ограничивает число кандидатов собственного банка. [Документация детектора](https://www.mathworks.com/help/lte/ref/ltenprachdetect.html).

Порог собственного банка калибруется на отдельном наборе 20000 шумовых окон для вероятности хотя бы одного false alarm 0.0005 на возможность. Независимая проверка выполняется ещё на 20000 окнах; сохраняется биномиальный интервал. Цель приёмки — верхняя граница 95% интервала не выше 0.001. Дополнительно проверяются помехи от разрешённых NPUSCH на соседних частотах: шумовая калибровка сама по себе не гарантирует устойчивость к межканальной помехе. Порог фиксируется до основных серий и не подгоняется под их ground truth.

## NPUSCH

| Настройка | Msg3 | Пользовательский TB | ACK/NACK для DL |
|---|---|---|---|
| Format | Data | Data | Control |
| Spacing | 15 kHz | 15 kHz | 15 kHz |
| Число поднесущих | 3 | 3 | 1 |
| Модуляция | QPSK | QPSK | BPSK |
| NRU | 1 | 4 | 1 |
| NULSlots | 8 | 8 | 4 |
| NRep | 2 | 2 | 2 |
| TBS | 88 bits | 256 bits | 1 bit UCI |
| Индекс | Msg3 RAR index 2 | MCS 4, `I_RU = 3` | Не используется |
| Длительность без разрывов | 8 ms | 32 ms | 4 ms |

Сочетания выбраны из [TS 36.213 Release 13, §16.3.3 и §16.5.1](https://www.etsi.org/deliver/etsi_ts/136200_136299/136213/13.13.00_60/ts_136213v131300p.pdf). RAR index не подменяет обычный MCS index. Группы Data — поднесущие 0:2, 3:5, 6:8, 9:11. Управляющий ACK/NACK использует ресурс, определённый полем DCI; при невозможности назначения переносится целиком вместе с соответствующим DL.

TB несёт 48-bit заголовок модели: packet sequence 16, fragment index 8, fragment count 8, valid payload length 8, reserved 8. Следовательно, полезная вместимость TB — 208 bits, пакет 1600 bits передаётся восемью TB: семь по 208 bits, последний 144 bits с 64 bits padding. Это собственная минимальная пакетная обёртка, не полная реализация RLC/MAC заголовков сети. Все 200 байт учитываются как полезные данные; обёртка и PHY CRC в throughput не включаются.

Msg3 несёт 48-bit contention token и 16-bit packet sequence, оставшиеся биты TB — padding. Token назначается UE случайно для попытки и проверяется на уникальность при генерации сценария; BS узнаёт его из декодированных битов. При коллизии BS не получает перечень реальных UE.

Приём использует оценки из DM-RS, компенсацию CFO и MMSE equalization, затем NPUSCH/NULSCH-декодирование. Переданные биты и истинный канал недоступны приёмнику. Практический тракт соответствует последовательности, показанной в [примере NPUSCH BLER](https://www.mathworks.com/help/lte/ug/nb-iot-npusch-block-error-rate-simulation.html). Для диагностики допускается отдельное сравнение с известным каналом, которое не используется для KPI основной модели.

Один HARQ-процесс на UE. Для Data разрешено четыре полных bundle-передачи TB с начальными RV 0, 2, 0, 2; каждый bundle содержит заданные два физических повторения. RV отдельных повторений внутри bundle вычисляется по §16.5.1.2 TS 36.213 для 15 kHz. Между bundle сохраняются soft buffers. Ретрансляции назначаются декодируемым N0 с прежним NDI; следующий TB использует новый NDI. Msg3 имеет один bundle в одной RA-попытке: после неуспеха применяется повтор RA через тайм-аут. `NTurboDecIts = 5`.

## Нисходящая линия

| Настройка | Принято |
|---|---|
| Antenna ports | `NBRefP = 1` |
| DCI | N0 для UL grants; N1 для NPDSCH |
| NPDCCH aggregation | Обе NCCE, один получатель на физический кандидат |
| Search space | Type-2 CSS во время RA; USS после RA |
| Search space configuration | `Rmax = 4`, `G = 8`, offset 0; календарь стартов из стандартной формулы |
| Фактические повторы NPDCCH | 2 |
| NPDSCH control | QPSK, MCS 6, NSF 1, TBS 88 bits, NRep 2 |
| RAR | Один RAPID, 15-bit UL grant, TA, Temporary C-RNTI; BI 256 ms |
| Msg4 | 48-bit contention identity и заголовок control element; padding до 88 bits |
| Data receipt | Тип 8 bits, packet sequence 16, итоговый fragment index 8, status 8, reserved 8; padding до 88 bits |
| DL feedback | NPUSCH Control, 2 повторения; Msg4 и receipt подтверждаются ACK |

Data receipt — сообщение исследовательской обёртки для подтверждения последнего TB; оно не объявляется отдельным стандартным NB-IoT ACK-каналом. Для промежуточных TB успешное декодирование следующего grant с новым NDI подтверждает завершение предыдущего. Receipt физически передаётся через NPDCCH/NPDSCH, при потере повторяется до четырёх попыток с интервалом 512 ms. Доставка на BS и получение подтверждения UE имеют разные временные метки. Уже доставленный пакет не превращается в dropped при потере receipt.

Номинальный интервал стартов search space составляет 32 ms. Таймеры в единицах `pp` реализуются по предусмотренному стандартом счёту мониторируемых NPDCCH-подкадров; фиксированные 320 или 512 ms не подставляются вместо этого счёта при пропусках обязательных подкадров. Используется календарь фактических monitoring opportunities.

DL резервирует обязательные подкадры NPBCH, NPSS, NSSS и SIB1-NB. Сетка SIB1 берётся для `schedulingInfoSIB1 = 0` из таблиц профиля; данные начальной конфигурации уже известны UE. В доступных для приёма окнах синтезируются NRS и реальные обязательные сигналы; NPBCH/SIB1 с фиксированными системными полезными данными также генерируются средствами Toolbox. UE не обязан проходить attach перед экспериментом. По всему горизонту заранее сохраняется маска доступности DL, чтобы служебные ресурсы не становились доступными Scheduler.

RA-RNTI, длина RAR grant, базовые задержки, поля DCI и TA выводятся из таблиц Release 13. Таймеры RAR/Msg4 и диапазон BACKOFF основываются на [TS 36.321, §5.1 и §7.2](https://www.etsi.org/deliver/etsi_ts/136300_136399/136321/13.02.00_60/ts_136321v130200p.pdf). Применение ненулевого BACKOFF без принятого BI, lifetime, лимит ожидания, фиксированные мощности и receipt являются явными решениями модели. Профиль воспроизводит исследуемую процедуру и физические каналы, но не заявляет полную сертификационную реализацию всего стека Release 13.

Счётчик RA увеличивается только при Msg1, а не при ожидании или вероятностном отказе от доступа. После восьмой неуспешной завершённой попытки пакет dropped. BS неуспехом CRC не уведомляет UE напрямую. До RAR UE ждёт своё окно; после Msg3 ждёт Msg4. Начатая, но не завершённая к горизонту попытка остаётся цензурированной. Уже доставленный на BS пакет сохраняется в локальном контексте UE до receipt или тайм-аута и до этого занимает место в лимите очереди: UE не освобождает его по скрытому знанию BS.

## Static и ресурсы

Согласованная единица ресурса — площадь полосы и времени за 500 ms отдельно в UL и DL. Политика постоянна: `P = 1`, RA 10%, DT 90%. RA включает Msg1/Msg2/Msg3/Msg4, N0/N1, относящиеся к RA, и ACK Msg4. DT включает пользовательские TB, их grants, retransmission grants, receipt и ACK receipt.

UL учитывается на сетке 3.75 kHz × 0.5 ms с объединением в группы 15 kHz. DL — целыми подкадрами 180 kHz × 1 ms после вычитания обязательных недоступных подкадров. RA-квота округляется вниз до базового элемента, DT получает остаток доступной площади. Неиспользованная квота не передаётся другой фазе и не переносится в следующее окно. Проверка передачи, пересекающей окно, выполняется по всем затронутым окнам до резервирования.

NPRACH резервируется заранее и уменьшает RA-бюджет. Остальные запросы упорядочиваются по ближайшему дедлайну, затем времени поступления, затем порядковому номеру запроса. Внутри одинакового дедлайна конкурирующие контексты обслуживаются циклически, чтобы один UE не занимал все последовательные grants. При нехватке ресурса запрос ожидает или истекает; невозможное назначение не сокращается и не выходит за квоту. Невыполнение запроса не изменяет Static.

UL и DL связанные сообщения резервируются транзакционно: grant, его передача и требуемый feedback должны быть возможны вместе. Выдача RAR без возможности Msg3 запрещена; выдача N1 без ресурсов NPDSCH/ACK также запрещена. Одному UE не назначаются пересекающиеся UL и DL; учитываются интервалы переключения и запрет приёма после UL.

Номинальная доля бюджета, реально зарезервированная площадь и фактическая занятость сохраняются отдельно. При совпадении Msg3 физическая occupancy считается по объединению ресурсов, а число передатчиков — диагностикой.

Сценарий 1000 UE с массовым приходом в 5 s сознательно перегружен. Его корректность не означает доставку всех 1000 пакетов: ожидаются waiting, unfinished и drops, обусловленные ресурсами и лимитами. Невозможность доставить все пакеты не оправдывает подмену WAVEFORM вероятностями или изменение квот.

## Трафик и эксперименты

| Сценарий | Настройки решения |
|---|---|
| Базовый массовый | Все UE получают один пакет; начало 1000 ms, длительность 100 ms; независимый равномерный приход внутри всплеска |
| Периодический | Один пакет каждые 1000 ms на UE, независимая равномерная исходная фаза |
| Пуассоновский | 0.2 пакета/s на UE; экспоненциальные интервалы, без принудительного пакета в t=0 |
| Low load | 100 UE, пуассоновский 0.05 пакета/s на UE |
| Всплески для sweep | N = 100, 500, 1000, 2500, 5000; длительность 10, 100, 500 ms |
| Датасет | Непересекающиеся окна 500 ms, включая окна без передач |
| Seeds серии | Первые 100 независимых внешних реализаций, производные от master seed 42 |
| Технический pilot | 3 реализации на комбинацию; затем 10; основная серия 100 при достаточных ресурсах |

Приходы непрерывного времени округляются вверх до 1 ms и сохраняются заранее; arrival на t=5000 ms не входит в полуоткрытый интервал генерации [0,5000). Размеры очередей, потерянные и незавершённые пакеты рассчитываются одинаково для всех типов трафика.

Primary target датасета — среднее по окну число UE с незавершённой RA или ожидающих её, включая BACKOFF. Дополнительные цели — среднее число всех UE с недоставленным пакетом, число фактических Msg1 и число уникальных передатчиков. Итоговый датасет хранит признаки BS отдельно от целей; train/validation/test 70/15/15 целыми реализациями. Разделение фиксируется заранее по `externalRealizationId` и сохраняется в manifest.

Случайность: `RandStream.create('mrg32k3a', 'NumStreams', 4096, 'StreamIndices', realizationId+1, 'Seed', masterSeed)` выбирает поток внешней реализации. Основные realizationId — 0–3999, калибровочные — 4000–4095. Источники, UE и время выбираются отдельными под-потоками. Ключ `1 + blockId + 2^24*(receiverId + 2^16*(directionCode + 2*sourceCode))` использует directionCode 0/1, receiverId 0–65535 и blockId 0–16777215; выход за пределы отклоняется. Коды источников 1–11: layout, traffic, shadowing, channel, CFO, timing, noise, payload, access, backoff, token. Для шума blockId — абсолютный тик 1 ms; остальные источники используют определённые в плане static/occasion/attempt ключи. Параметры стационарного канала выбираются один раз на UE/направление. Порядок обработки не меняет внешнюю реализацию. Механизм независимых потоков описан в [документации RandStream.create](https://www.mathworks.com/help/matlab/ref/randstream.create.html); выбранные ключи относятся к этому проекту.

Время расчёта не ограничивается выдуманной оценкой. Pilot измеряет секунды/запуск, память и долю времени PHY; manifest оценивает стоимость серии. Последовательная версия обязательна. Параллельная — отдельная последующая оптимизация при наличии Toolbox.

## Правила изменения профиля при разработке

Проектные параметры уже выбраны; повторные вопросы пользователю для их утверждения не требуются. При выявленной несовместимости локального Toolbox или стандарта инженер исправляет конкретное значение минимально необходимым образом и записывает причину, источник и новую версию профиля. Нельзя молча менять правило сравнения, убрать физическую передачу управляющих сообщений, выдать истину приёмнику или увеличить ресурсную квоту ради желаемого KPI.

Метрики, корреляционные пороги, пропускная способность и работоспособность установки здесь не подтверждены выполнением. Все численные эксперименты и проверки перечислены в плане будущей реализации.
