# Протокол сравнения трёх режимов

Документ описывает подготовку и запуск сравнения Static, Adaptive-P и Adaptive-RA/DT. Полная научная серия выполняется на другой машине после проверки модели и согласования вычислительного бюджета. Здесь допустимы только проверка плана без симуляции и короткие случаи в местном лимите.

## Что сравнивается

Для каждого сочетания числа устройств, длительности всплеска и независимого внешнего ID программа запускает выбранные режимы на одной и той же заранее построенной сцене. Меняется политика управления; размещение, начальная среда и подготовленные случайные условия передаются всем режимам совместно.

Зафиксированная сетка сравнения — нагрузки `100/500/1000/2500/5000` устройств и всплески `10/100/500` мс. При 100 независимых ID и трёх режимах она содержит 4500 случаев. Это план будущего сравнения, не запуск: `designOnly=true` не выполняет ни одного случая и не резервирует ID.

## Группы данных и роли ID

Разделение делается по целому внешнему ID, до сборки таблицы. Все нагрузки, трафик, методы и окна одного ID остаются в одной группе; почти одинаковые окна одного сценария не могут попасть одновременно в обучение и проверку.

| Набор | Группа `split` | Роль опыта | Доля ID | Использование |
|---|---|---|---:|---|
| Обучение модели | `train` | `training` | 70% | Подгонка моделей и обучение заполнения пропусков/масштабирования |
| Проверка кандидата | `validation` | `validation` | 15% | Выбор модели и настройка политики управления |
| Контроль моделей | `test` | `model-test` | 15% | Однократная независимая оценка заранее зафиксированных кандидатов |
| Итоговое сравнение режимов | `test` | `final-comparison` | отдельные 100 ID | Только сравнение Static, Adaptive-P и Adaptive-RA/DT после фиксации модели и правил |

Три группы для моделей составляют один непересекающийся набор ID в отношении 70/15/15. Для точных долей размер этого набора выбирается кратным 20; сколько ID реально нужно, решают по покрытию сценариев и точности на validation в согласованном бюджете. Отдельные 100 ID `final-comparison` не входят в этот набор и не используются для обучения, выбора модели, порогов или правил. Числа ID заранее не назначены: перед запуском их проверяют и выделяют через `realizationRegistry.json`; список групп сохраняется в manifest. Занятые, зарезервированные и уже использованные ID повторно не назначают.

Четыре модели обучают только на `train`; кандидата выбирают по `validation`. Все кандидаты и их настройки фиксируют до просмотра `model-test`; его оценки не используют для выбора модели или порогов. Если результат `model-test` приводит к изменению модели или правил, этот набор больше не считается независимым контролем: нужна новая группа ID. Итоговые 100 `final-comparison` ID держат закрытыми до фиксации выбранного пакета модели, его SHA-256, схемы признаков, конфигурации, калибровки, правил Adaptive, исходников и метрик. После этого сравнение не перенастраивают по его результатам.

Исполнитель сравнения включает в хеш плана матрицу, ID, методы, конфигурацию, временные ограничения, калибровку, модель, политику и исходники. Изменение любого из этих входов создаёт другой план и блокирует продолжение старого.

Для каждого случая сводка сохраняет доставку и потери пакетов, успешность и коллизии доступа, среднее и 95-й процентиль задержки, скорость передачи, ошибки Msg3/Data, занятость UL/DL/NPRACH, очереди BS/UE, повторы HARQ и решения контроллера. Значения по каждому режиму сводятся по независимым ID: показываются число полных и неполных случаев, среднее и интервал. Для Static показатели контроллера помечаются как неприменимые. Парное сравнение считает разность `второй режим − первый` для одинакового независимого ID. При одной паре интервал не строится. Failed, stopped и отсутствующие пары остаются видны как неполные.

## Безопасная проверка плана

Для dry-run нужны существующие файлы калибровки, реестра ID и пакета модели. Пакет модели только хешируется для идентичности плана: при `designOnly=true` симуляция и проверка качества модели не выполняются. Папка вывода должна быть новой или содержать только два файла плана.

Пример ниже строит план, но не выделяет ID и не запускает расчёты. Диапазон `1200:1999` — только список кандидатов; код отбирает из него свободные ID. Перед реальным запуском ID нужно закрепить одним реестром и одним исполнителем. Значения времени в блоке предназначены только для dry-run и не являются бюджетом будущей серии.

```matlab
setupProject();
root = pwd;
registryFile = fullfile(root, 'experiments', 'realizationRegistry.json');
modelFile = fullfile(root, 'verification', 'external', 'model', 'bundle.mat');
if ~isfile(modelFile)
    error('Замените modelFile на путь к существующему пакету модели перед dry-run.');
end
candidateIds = 1200:1999;
freeIds = nbiot.experiments.availableRealizationIds( ...
    registryFile, 'final-comparison', candidateIds);
if numel(freeIds) < 100
    error('Нужно выбрать 100 непересекающихся ID после проверки реестра.');
end

execution = struct('profile', 'external-machine', ...
    'role', 'final-comparison', 'maxUE', 5000, ...
    'maxCaseSeconds', 300, 'maxSuiteSeconds', 2000000000);
options = struct('designOnly', true, ...
    'counts', [100 500 1000 2500 5000], ...
    'burstDurations', [10 100 500], ...
    'methods', ["Static" "Adaptive-P" "Adaptive-RA/DT"], ...
    'realizationIds', freeIds(1:100), ...
    'calibrationFile', fullfile(root, 'results', 'nprach-calibration.mat'), ...
    'modelFile', modelFile, ... % Путь к существующему пакету; dry-run его не запускает.
    'execution', execution, 'registryFile', registryFile, ...
    'outputFolder', fullfile(root, 'verification', 'external', 'comparison-design'));
plan = runComparisonSweep(options);
assert(plan.designOnly && plan.caseCount == 4500);
```

`modelFile` в примере нужно задать заранее существующим `.mat`-пакетом. `modelFile` и временные лимиты в этом примере нельзя переносить в реальный запуск без замены на принятую модель и измеренный бюджет целевой машины. Dry-run проверяет форму матрицы и доступность кандидатов, но не закрепляет выбранные ID.

## Исполнение и продолжение

Физический запуск разрешён только после независимой проверки модели, фиксирования правил управления и выбора новой группы ID. `designOnly` нужно переключить в `false`, затем заменить временные лимиты на измеренные и явно указать `resume=true`. Перед созданием выхода программа проверяет бюджет, модель и доступность ID; при выполнении сохраняет manifest после каждого случая. Повтор с той же моделью, калибровкой, правилами, исходниками, матрицей и ID продолжает ту же коллекцию. Изменение этих входов блокирует продолжение.

Результаты хранятся в `comparison-manifest.mat` и `comparison-manifest.csv`; каждый физический случай лежит в отдельной подпапке и проверяется через `verifyCase`. После успешного завершения вызвать `plotComparisonSummary(manifest, outputFolder)`. Она создаёт `method-summary.csv`, `paired-comparison.csv` и `comparison-summary.png`. Вкладка **Сравнение режимов** в окне открывает папку с этими файлами и показывает сводки без повторного моделирования.

## Текущее ограничение

Dry-run полной матрицы проверен без запуска случаев; `TestComparisonSweep` прошёл 5/5. Выгрузка расширенных показателей проверена на сохранённых тестовых таблицах (`TestComparisonSummaryLoading`, 3/3), их список и русские подписи в интерфейсе — `TestNBIoTAppComparisonSummary`, 2/2. Разделение ролей и правило фиксации модели описаны выше, но реальные ID ещё не выделены. На момент обновления код умеет запускать Adaptive только с development-моделью в профиле `local-development`. Проверенной на реальных данных и принятой модели пока нет, а обычный внешний Adaptive-запуск намеренно не разрешён. Поэтому готовая матрица — план, а не основание запускать серию. Владелец отложил физические серии до отдельного решения; после его возобновления потребуются обучение/оценка модели и согласованный бюджет.
