## 1. Аннотация

**Цель:** среда имитационного моделирования и численных экспериментов для системы адаптивного контроля
нагрузки в сетях NB-IoT.

- Среда: **MATLAB + LTE Toolbox**.
- Единственная модель радиоинтерфейса — **физическая WAVEFORM-модель** (формирование, передача, канал,
  обработка NB-IoT сигналов на уровне отсчётов).
- Воспроизводимое моделирование множества UE, разных типов нагрузки, RA, передачи данных, изменения
  состояния устройств и сети во времени, оценки нагрузки, работы интеллектуального контроллера.

**Задачи (13):** сценарий развертывания UE; генерация трафика и изменения нагрузки; модель состояний UE;
WAVEFORM-модель NPRACH; физическое моделирование NPUSCH; радиоканал и link budget; ML-оценка нагрузки по
результатам NPRACH и др. признакам; интеллектуальный контроллер; Adaptive-P; Adaptive-RA/DT;
численное моделирование при разных нагрузках; сравнение адаптивных методов со Static; сравнение двух
адаптивных методов между собой.

**Основные характеристики обслуживания:** вероятность успешной попытки доступа; вероятность успешной
передачи данных; пропускная способность.

**Дополнительно:** вероятность коллизии, число повторных попыток, задержка, вероятность потери пакета,
загрузка радиоресурсов, длина очереди, BLER, число переключений контроллера, прочее.

**Итог:** MATLAB-прототип: единая WAVEFORM-модель NB-IoT, сценарий UE, модели нагрузки и доступа,
физические NPRACH и NPUSCH, ML-модуль, контроллер, два адаптивных метода, Static, средства экспериментов,
сбора результатов и сравнительного анализа.

## 2. Актуальность (кратко)

NB-IoT — много устройств, малые объёмы, длительная низкая активность + всплески массового доступа.
Рост конкуренции за NPRACH → коллизии, повторы, задержки. Статическая конфигурация не учитывает
динамику. Нужна воспроизводимая среда, учитывающая физику (канал, мощность, задержки, CFO, шум,
одновременная передача нескольких UE).

## 3. Проблема

Нужно динамически менять параметры системы при изменении числа активных UE и интенсивности данных.
Число наблюдаемых коллизий не однозначно определяет нагрузку, т.к. результат приёма NPRACH зависит от:
положения UE, расстояния до BS, потерь распространения, затенения, проникновения, мощности, параметров
канала, временной задержки, CFO, взаимного влияния UE, шума. → Признаки из физического моделирования
NPRACH + ML для оценки нагрузки → контроллер выбирает параметры управления.

## 7. Объект и предмет

- Объект: обслуживание UE в NB-IoT при изменяющейся нагрузке.
- Предмет: методы оценки нагрузки и адаптивного управления параметрами RA и распределением ресурсов RA/DT.
- Логические процессы (трафик, состояния UE, контроллер, статистика, решения) — программные модули,
  взаимодействующие с физической моделью радиоинтерфейса.

## 8. Термины

RA — случайный доступ; NPRACH — физ. канал RA; NPUSCH — восходящий канал данных; NPDSCH — нисходящий
канал; NPDCCH — управляющая информация; DT — фаза передачи данных; UE — оконечное устройство.

**Последовательность доступа:** Msg1 NPRACH → Msg2 RAR (NPDCCH/NPDSCH) → Msg3 (NPUSCH) →
Msg4 (NPDCCH/NPDSCH). Затем пакет по NPUSCH; доставлен ⇔ успешное декодирование + CRC.

## 9. Общая структура

Цепочка: Traffic Generator → Device State Machine → NPRACH Waveform → Radio Channel →
NPRACH Receiver/Analysis → Load Estimation → ML Predictor → Adaptive Controller → Resource Allocation →
NPDCCH/NPDSCH/NPUSCH → Metrics.

Модули (20): генератор трафика; модель устройств; геометрия соты; link budget; радиоканал;
NPRACH TX; NPRACH RX; анализатор NPRACH; NPUSCH TX; NPUSCH RX; управляющая линия; планировщик;
анализатор коллизий; ML; контроллер; статическая модель; сбор метрик; визуализация; GUI; тестирование.
Все — в едином сценарии.

## 11. Нагрузка и трафик

- 11.1 Периодический — пакеты через заданный период.
- 11.2 Пуассоновский — экспоненциальные межприходные интервалы.
- 11.3 Массовый — группа UE формирует пакеты в коротком интервале (всплеск).

Параметры: число устройств, интенсивность, размер пакета, момент начала всплеска, длительность всплеска,
распределение активности UE, макс. размер очереди. **Основной сценарий — массовый доступ.**

## 12. Модель состояний UE

| Состояние | Описание |
|---|---|
| IDLE | Нет пакета |
| WAIT_RA | Ожидание возможности RA |
| RA_TX | Формирование и передача NPRACH |
| RA_PROCESSING | Обработка результата доступа |
| BACKOFF | Ожидание повторной попытки |
| WAIT_RAR | Ожидание RAR |
| MSG3_TX | Передача Msg3 по NPUSCH |
| WAIT_CONTENTION_RESOLUTION | Ожидание Msg4 |
| WAIT_GRANT | Ожидание назначения ресурсов |
| DATA_TX | Передача данных |
| DONE | Пакет доставлен, CRC пройден |
| DROPPED | Отброшен по лимиту попыток или тайм-ауту |

- Базовый: IDLE → WAIT_RA → RA_TX → RA_PROCESSING.
- Неуспех: RA_PROCESSING → BACKOFF → WAIT_RA.
- Успех: RA_PROCESSING → WAIT_RAR → MSG3_TX → WAIT_CONTENTION_RESOLUTION → WAIT_GRANT → DATA_TX → DONE.
- Превышение лимита попыток или времени обслуживания → DROPPED.

## 14. WAVEFORM-модель NPRACH

Единственный режим физического моделирования. Для каждого UE:
1. выбор ресурса NPRACH; 2. выбор преамбулы; 3. формирование waveform; 4. масштабирование по мощности;
5. временная задержка; 6. CFO; 7. индивидуальная реализация канала; 8. суммирование одновременных сигналов;
9. шум; 10. обработка принятого сигнала; 11. обнаружение NPRACH; 12. классификация результата.

Формирование и обработка — **средствами LTE Toolbox**.
Учитывать: уровни принимаемой мощности, расстояния, временные смещения, CFO, fading, shadowing,
одновременную передачу нескольких UE, различие их мощностей, шум приёмника.

Классы результата: успешное обнаружение; miss; успешный доступ; логическая коллизия; capture; false alarm.

## 15. Анализ NPRACH и коллизий

Определять: число попыток; обнаруженные преамбулы; недетектированные; коллизии; успешные доступы;
повторные попытки; P(коллизии); P(обнаружения); P(успешного доступа).

Отдельно учитывать: ≥2 UE с одной преамбулой; ≥2 UE с разными преамбулами; равные мощности;
сильно различающиеся мощности; timing offset; CFO; комбинации факторов.

## 16. Capture effect и near-far

Несколько одновременных сигналов, один существенно сильнее. Определить: зависимость обнаружения от
разности мощностей; P(приёма сильного); P(приёма слабого); влияние timing offset, CFO, канала.
Зависимости используются при верификации физической модели.

## 17. Timing offset и CFO

Индивидуальные для каждого UE. Исследовать влияние на P(обнаружения), P(коллизии), P(успешного доступа),
P(miss). CFO ~ N(0, 50²) Гц, ограничение ±200 Гц. Параметры меняются в сценарии.

## 18. Процедура случайного доступа

UE → NPRACH → detection → RAR → Msg3 → contention resolution → grant → data transmission.

Для каждой попытки хранить: время начала; ресурс; преамбулу; результат физ. обнаружения; коллизию;
capture; результат RAR; результат Msg3; число попыток; время до успеха или отказа.
При неуспехе — BACKOFF. Макс. число попыток — параметр.

## 19. NPDCCH/NPDSCH

NPDCCH — управляющая информация; NPDSCH — нисходящие сообщения (RAR, contention resolution).
Учитывать: формирование управляющего сообщения, назначение ресурсов, передачу, приём, результат
декодирования. Согласованность NPRACH → RAR → Msg3 → contention resolution.

## 20. NPUSCH

Передаёт Msg3 и данные. Для пакета: 1) назначение ресурса; 2) формирование; 3) канал; 4) приём;
5) декодирование; 6) CRC; 7) фиксация успеха/неуспеха. Критерий успеха — декодирование + CRC.
Дополнительно — BLER.

## 21. Методы ML

Оценка текущей нагрузки по признакам, доступным BS. Датасет формируется в ходе моделирования.
Известное в симуляции число активных/конкурирующих UE — ground truth.

Признаки: статистики NPRACH, число попыток, доля успешных обнаружений, коллизии, повторные попытки,
occupancy, длины очередей, задержки, число активных UE*, результаты передачи данных, доп. признаки.
(*см. §40 — истинное число активных UE не должно попадать в признаки online-контроллера, если оно target.)

Модели: Linear Regression, Decision Tree, Random Forest, Gradient Boosting.
Для каждой: обучающая выборка, тестовая выборка, целевая переменная, набор признаков, метрики ошибки,
качество на независимой тестовой выборке.

## 22. Датасет

Запись = временной интервал моделирования. Минимум: timestamp, число активных UE, попытки NPRACH,
обнаруженные преамбулы, коллизии, успешные доступы, повторные попытки, occupancy, средняя длина очереди,
средняя задержка, прочие признаки. Target: фактическое число активных/конкурирующих UE или показатель
нагрузки. Формируется автоматически и сохраняется.

## 23. Интеллектуальный контроллер

Запуск периодический, базово **500 мс**. Вход: оценка нагрузки, число активных UE, статистика NPRACH,
P(коллизии), повторные попытки, длины очередей, задержка, occupancy, текущая конфигурация.
Выбирает **допустимое решение из заранее определённого множества** на основе состояния и ML-оценки.

## 24. Adaptive-P

Динамическое изменение вероятности передачи преамбулы UE. Рост нагрузки → уменьшение p; снижение → рост.
p — из заданного набора или по алгоритму. Исследовать влияние на: P(успешного доступа), P(успешной
передачи данных), throughput, P(коллизии), среднее число попыток, задержку, потери, загрузку ресурсов.

## 25. Adaptive-RA/DT

Динамическое изменение доли ресурсов RA и DT. Базовые конфигурации: **10/90, 20/80, 30/70**.
Контроллер выбирает конфигурацию по оценке нагрузки и состоянию. RA/DT — логическая политика
распределения ресурсов фаз; **сетки UL и DL не объединяются в одну физическую сетку**.
Исследовать влияние на: P(успешного доступа), P(успешной передачи), throughput, P(коллизии), задержку,
повторные попытки, загрузку ресурсов.

## 26. Static

Не меняется в эксперименте. Базово **RA/DT = 10/90**, остальное неизменно.
Сравнения: Static vs Adaptive-P; Static vs Adaptive-RA/DT; Adaptive-P vs Adaptive-RA/DT.

## 27. KPI

Основные:
- 27.1 P(успешного доступа) — доля попыток RA, завершившихся успешной RA-процедурой.
- 27.2 P(успешной передачи данных) — доля пакетов, переданных и подтверждённых CRC.
- 27.3 Пропускная способность — успешно переданные данные за единицу времени.

Дополнительные: P(коллизии); среднее число попыток; средняя задержка; 95-й процентиль задержки;
P(потери пакета); доля доставленных; NPUSCH BLER; загрузка UL; загрузка DL; occupancy NPRACH;
средняя и максимальная длина очереди; число решений контроллера; число переключений конфигурации.

## 28. Методика экспериментов

Единая WAVEFORM-модель. Для всех сравниваемых сценариев одинаковые: координаты UE, параметры трафика,
размеры пакетов, начальные состояния UE, параметры канала, shadowing, fading, шум, CFO, timing offset,
начальные состояния очередей, seed и внешние случайные реализации.
**Различие Static/Adaptive — только алгоритм управления.**

## 29. Уровни нагрузки

100, 500, 1000, 2500, 5000 UE; разные интенсивности массового трафика; при необходимости промежуточные.
**Не менее 100 независимых реализаций** на основной сценарий (если позволяют ресурсы).

## 31. Проверка размещения UE

1) заданное количество; 2) все внутри соты; 3) мин. расстояние; 4) корректность распределения;
5) доля indoor; 6) корректность координат; 7) воспроизводимость при seed; 8) идентичность для Static и
Adaptive. Результаты — в отчёт.

## 32. Проверка link budget

Расстояние, path loss, shadowing, penetration, мощность передачи, принимаемая мощность, шумовая мощность,
SNR/SINR, влияние fading, indoor/outdoor. Тестовые случаи с аналитически проверяемыми параметрами.

## 33. Проверка NPRACH waveform

1) формирование; 2) передача одного UE; 3) приём одного UE; 4) обнаружение преамбулы; 5) шум;
6) разные мощности; 7) разные timing offset; 8) разные CFO.
**Loopback-тест:** NPRACH TX → канал/искажения → NPRACH RX.

## 34. Проверка коллизий NPRACH

Сценарии: 1) два UE — одна преамбула одновременно; 2) несколько UE — одна преамбула; 3) два UE — разные
преамбулы; 4) разные мощности; 5) разные timing offset; 6) разные CFO. Проверять классификацию приёма.

## 35. Проверка capture/near-far

Варьировать ΔP = P_strong − P_weak. Проверять: обнаружение сильного, слабого; P(успешного доступа);
P(коллизии); зависимость от timing offset и CFO.

## 36. Проверка timing offset и CFO

Серии по timing offset, CFO, SNR, принимаемой мощности. Зависимости — монотонные или физически
объяснимые. Все параметры сохраняются вместе с результатами.

## 37. Проверка конечного автомата UE

Для каждого состояния: вход, допустимые переходы, выход, отсутствие недопустимых переходов, обработка
ошибок. Отдельно: IDLE→WAIT_RA→RA_TX→RA_PROCESSING; failure→BACKOFF→WAIT_RA;
success→RAR→MSG3→contention resolution→DATA_TX→DONE.

## 38. Проверка BACKOFF и лимита попыток

Переход в BACKOFF, длительность ожидания, повторная попытка, счётчик, максимум попыток, переход в DROPPED,
отсутствие бесконечного цикла. Базовый максимум: 8.

## 39. Проверка NPUSCH и CRC

1) формирование; 2) передача; 3) канал; 4) приём; 5) декодирование; 6) CRC; 7) фиксация успеха;
8) фиксация ошибки. CRC success → delivered; CRC failure → not delivered / повтор по модели.

## 40. Проверка ML

Корректность признаков; **отсутствие утечки ground truth в признаки**; корректный train/test split;
воспроизводимость обучения; качество прогноза; ошибка оценки нагрузки.
Истинное число активных UE не передаётся в признаки online-контроллера, если оно target.

## 41. Проверка контроллера

Запуск; периодичность; получение признаков; получение ML-оценки; выбор допустимого решения; изменение
параметров системы; сохранение истории; отсутствие недопустимых конфигураций. Период 500 мс.

## 42. Воспроизводимость

При фиксированном seed воспроизводятся: координаты UE, трафик, начальные состояния, параметры канала,
CFO, timing offset, выбор UE, формирование RA. Повторный запуск = одинаковый результат в пределах
численной точности.

## 44. Итоговая комплексная проверка
